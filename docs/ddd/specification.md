# 仕様(Specification)

Specificationパターンとは、「あるオブジェクトが特定の条件を満たすかどうか」を判定するルールを、それ自体を1つのオブジェクトとしてカプセル化するパターンです。Evansは*Domain-Driven Design*の中で、述語(true/falseを返す判定ロジック)がドメインルールとして重要になり、かつ複数の場所(検索条件・生成時の検証・コレクションからの選別など)で再利用されるとき、その述語をエンティティや値オブジェクトのメソッドとしてではなく独立したSpecificationオブジェクトとして切り出すことを提案しています。FowlerもPoEAAの周辺で同種のアイデアを説明しており、複数のSpecificationを`And`/`Or`/`Not`で合成できる点が特徴として挙げられます。

## 典型的な用途

- 検索条件の組み立て(例: 「在庫があり、かつ特定カテゴリに属する商品」といった条件をオブジェクトとして組み合わせる)
- 集約生成時の検証条件の再利用(生成時のチェックと、生成後の状態が条件を満たすかのチェックを同じロジックで行う)
- リポジトリへの問い合わせ条件の抽象化(SQLの`WHERE`句を直接書かずに、ドメイン語彙で条件を表現する)

## 本リポジトリでは採用していません

`internal/domain`配下のいずれのコンテキストにもSpecificationパターンの実装は存在しません。理由は次の2点です。

**フィルタ・検索条件はCQRSのクエリサービスに閉じている。** 本リポジトリは軽量CQRS([cqrs.md](cqrs.md)参照)を採用しており、読み取り(query)はドメイン層を経由せず`internal/infrastructure/persistence/*_query_service.go`が直接DTOを組み立てます。しかも現状のクエリサービスは`List`と主キー1つによる`FindByID`(または`FindByCustomerID`/`FindByCode`など単一キー)しか持たず(例: [catalog_query_service.go](../../internal/infrastructure/persistence/catalog_query_service.go)の`ProductQuery.List`/`FindByID`)、複数条件を組み合わせて絞り込むような検索は1つも実装されていません。条件を組み合わせる必要がある検索が実際に存在しないため、条件をオブジェクト化して再利用・合成するSpecificationの出番がありません。

**各コンテキストが単一の集約しか持たず、ルールが単純である。** [domain-service.md](domain-service.md)でも触れている通り、本リポジトリの各コンテキスト(catalog / cart / order / customer / inventory / shipping / coupon)はそれぞれ集約を1つずつしか持ちません。集約が守る不変条件も「reserved <= quantity」(`inventory.Stock`)や「デフォルト住所は必ず1つ」(`customer.Customer`)のように、集約自身のメソッド内で完結する単純な条件です。複数箇所(生成時の検証・検索条件・コレクションからの選別)で同じ判定ロジックを再利用する必要がある場面が構造的に発生していないため、判定ロジックを独立したオブジェクトに切り出す動機がありません。

これら2つの理由により、Specificationを導入する必然性のある実装が本リポジトリには存在しません。ここで無理に「在庫が十分にある商品を選ぶSpecification」のような例を作ることもできますが、それは実際の要求から生まれたものではない人工的な例(パターンのための実装)になってしまいます。本リポジトリは「原則から外れている箇所を、外れていると正確に説明できる状態にする」ことを目的としており([specs/ddd-improvements.md](../specs/ddd-improvements.md)参照)、学習コストを上げるだけの人工例を集める("pattern-collecting")よりも、実例のないパターンは「なぜ実例がないか」を明記する方針を一貫して取っています([domain-service.md](domain-service.md)、[domain-event.md](domain-event.md)も同じ扱いです)。

## 注意点・よくある誤解

- Specification不採用は実装漏れではなく、「必要になる場面が現状のコードにない」という監査結果です。ドメインルールの判定自体(`Stock.Reserve`の在庫充足チェックなど)は各集約のメソッド内にあり、消えているわけではありません。
- 将来、検索条件が複雑化する場面(例: 「在庫があり、かつ特定カテゴリに属し、かつ割引対象である商品」を横断的に検索したい)が生まれたら、クエリサービスの引数に条件オブジェクトを渡す形でSpecificationの導入を検討するのが自然な流れです。ただしその場合も、CQRSのquery経路はドメイン集約を経由しない設計であるため、Specificationは「ドメイン集約の不変条件判定」としてではなく「クエリ条件の合成」としての役割が主になります。
- Specificationは値オブジェクト([value-object.md](value-object.md))の一種として実装されることが多いパターンですが、本リポジトリの値オブジェクトの実例はすべてMoneyやID型のような「値そのもの」であり、「判定ロジックを持つ値オブジェクト」の実例はありません。
