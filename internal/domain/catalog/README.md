# catalog コンテキスト

catalog は「どんな商品が存在し、いくらで売られているか」を管理する
境界づけられたコンテキスト（Bounded Context）である。

## 集約境界（Aggregate Boundary）

このコンテキストの集約ルートは `Product` の 1 つだけであり、集約の
範囲は「1 商品分の名前・説明・価格」に閉じている。

在庫数や在庫予約のような「他の書き込みトランザクションと強く絡む」
概念はあえて Product に含めていない。もし在庫を Product に持たせると、
在庫の増減のたびに Product 全体をロックすることになり、商品情報の
更新（名前修正など）と在庫更新が不必要に競合してしまう。DDD では
「同時に一貫性を保つ必要がある範囲」だけを 1 つの集約にまとめるべき
とされており、在庫が必要になった場合は別の集約（例: Stock）として
切り出すのが定石である。

cart コンテキストなど他のコンテキストは、Product 集約そのものを
参照するのではなく `ProductID` という識別子だけを保持する。これにより
コンテキスト間の結合を弱く保ち、catalog 側の内部実装（Product の
フィールド構成など）を変更しても他コンテキストに影響が及ばないように
している。

## 不変条件（Invariant）

`Product` が常に守る業務ルールは次の 2 つである。

- 商品名は必須であり、100 文字以内である
- 商品説明は 1000 文字以内である

価格の非負性は `Product` 自身ではなく `shared.Money` 値オブジェクトが
保証する（負の金額を持つ `Money` はそもそも生成できない）。集約は
「その集約に固有のルール」だけを持ち、値オブジェクト自身が守れる
ルールは値オブジェクトに委譲するのが望ましい責務分担である。

## なぜ価格を `Money` 値オブジェクトで表現するのか

価格を単なる `int64` として持つと、「通貨単位を取り違える」
「マイナスの金額を許してしまう」といった不正な状態をコンパイラも
実行時チェックも防いでくれない。`shared.Money` を使うことで、

- 通貨単位（`Currency`）を金額と常にセットで扱える
- 負の金額を生成しようとした時点でエラーになる
- `Add` / `Multiply` のような金額計算を値オブジェクトのメソッドとして
  一箇所にまとめられる

というメリットが得られる。これは「プリミティブ型への執着
（Primitive Obsession）」という典型的なアンチパターンを避けるための
DDD の基本テクニックである。
