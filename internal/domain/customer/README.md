# customer コンテキスト（ドメイン層）

customer は「顧客が誰で、どの住所に配送できるか」を管理する境界づけられた
コンテキスト（Bounded Context）である。本リポジトリの中で、このコンテキスト
は「子エンティティを持つ集約（Aggregate）」の設計をもっとも典型的な形で
示すショーケースとして書かれている。

## なぜ Customer + Address が集約のショーケースなのか

`cart.Cart` の明細（`CartItem`）や `order.Order` の明細（`OrderItem`）も
広い意味では「集約ルートが内部に抱える子要素」だが、識別子を持たず
値オブジェクトに近い性質が強い（`CartItem`/`OrderItem` は生成後に
書き換えられるフィールドがほとんどない）。

対して `customer.Address` は次の 2 点で「エンティティらしいエンティティ」
である。

1. 独自の識別子 `AddressID` を持つ（「どの住所か」を名指しで扱える）。
2. 生成後も `isDefault` フラグが書き換わる、つまり寿命の中で状態が変化する。

そして最も重要な点として、`Customer` 集約は次の不変条件を持つ。

> デフォルト住所は、住所が 1 件でもあれば必ずちょうど 1 つ存在する。

この条件は `Address` を 1 件だけ見ても判定できない。「他の兄弟住所が
デフォルトになっていないか」という、集約全体を横断した整合性チェックが
必要だからである。これはまさに DDD が「集約」という概念をわざわざ用意する
理由そのものである。

## ルート経由の操作強制

`Address` にはフィールドを直接書き換えるメソッドを一切公開していない
（`isDefault` を立てる／降ろす操作も非公開）。`Address` を新しく作る唯一の
経路は `Customer.AddAddress`、状態を変える唯一の経路は
`Customer.ChangeDefaultAddress` / `Customer.RemoveAddress` である。

これにより、以下のような「集約の外から直接子エンティティを書き換えて
不変条件を壊す」ことがコンパイル時に不可能になる。

```go
// このようなコードは書けない（フィールドが非公開のため）。
addr := customer.Address{ /* ... */ }
addr.isDefault = true
```

## 不変条件の置き場所

- **住所は最大 5 件まで**: `Customer.AddAddress` が件数を数えてから追加する。
  `Address` 自身は「自分が何番目の住所か」を知らないため、この判断は
  必ず集約ルートが持つ必要がある。
- **デフォルト住所は住所があれば必ず 1 つ**:
  - 最初の 1 件を追加した瞬間、`AddAddress` が自動的にデフォルトへ
    昇格させる。「住所を追加したのに、まだ誰もデフォルトを選んでいない」
    という不変条件違反の状態を一切作らないための設計判断である。
  - `ChangeDefaultAddress` は「既存のデフォルトを降ろす」「新しい
    デフォルトを立てる」という 2 つの書き換えを 1 回のメソッド呼び出しの
    中でアトミックに行う。この 2 ステップを外部（アプリケーション層）に
    分割して行わせると、その途中の瞬間に「デフォルトが 0 個」または
    「デフォルトが 2 個」という不整合が一時的にせよ発生しうる。
  - `RemoveAddress` は、削除後も他の住所が残る場合、デフォルト住所の
    削除を拒否する。これは「デフォルトが不在になる」か「システムが
    勝手に別の住所を新デフォルトに昇格させる」かのどちらかを選ばざるを
    得なくなるためであり、後者は顧客本人の意思決定をシステムが肩代わり
    してしまう危険な自動化である。一方、最後の 1 件を削除する場合は
    住所が 0 件になるだけで不変条件の前提自体が崩れるため、削除を許す。

## 境界＝トランザクション整合性の単位

`Customer` と `Address` は必ず 1 つのトランザクションの中でまとめて
読み書きされる（`internal/infrastructure/persistence/customer_repository.go`
の `Save` を参照）。他のどの集約（cart, order, ...）も、customer
コンテキストが所有する `Address` テーブルを直接更新することはない。
「1 回のドメイン操作 = 1 つの集約 = 1 トランザクション」という原則を
守ることで、`Customer` 集約に閉じたルールの整合性を、DB レベルの
複雑なロックや分散トランザクションなしに保証できる。

## catalog / cart / order への依存を持たない

`customer` パッケージは他のどのコンテキストの domain パッケージも
import しない。顧客が誰であるかは、注文（order）やカート（cart）が
`CustomerID` という軽量な ID を通じて参照する側であり、逆に customer
コンテキストが注文やカートの中身を知る必要はない。これは
`order/README.md` に記した「コンテキストの自律性」と同じ原則である。
