# coupon コンテキスト（ドメイン層）

## 値オブジェクト: CouponCode

`CouponCode` は「4〜20 文字、大文字英数字とハイフンのみ」というクーポンコードの
形式ルールを閉じ込めた値オブジェクトである。もしこのルールを各所（プレゼン
テーション層の入力検証、永続化層の復元処理など）に個別のバリデーション関数
として散らばらせてしまうと、チェックを書き忘れた箇所から不正な形式のコード
が紛れ込む余地が生まれる。`NewCouponCode` を通過して一度 `CouponCode` 型の
値を得られれば、それだけで「正しい形式のコードである」ことが型として保証さ
れ、以降の呼び出し側（`Coupon` 集約や検索処理）は再検証を意識しなくてよい。

## 2 種類の割引方式の設計

クーポンには「固定金額を割り引く」（`amount` 型）と「合計金額に対する割合で
割り引く」（`rate` 型）の 2 種類がある。この 2 つは Coupon 構造体の中で
`amount` / `ratePercent` という別々のフィールドとして共存しているが、
実際に意味を持つのはどちらか一方だけである（amount 型では `ratePercent` は
未使用、rate 型では `amount` は未使用）。

この「一方だけが有効」という不変条件を守るために、`NewAmountCoupon` と
`NewRateCoupon` という 2 つの専用コンストラクタを用意している。単一の
`NewCoupon(discountType, amount, ratePercent, ...)` のようなコンストラクタ
1 つにまとめてしまうと、「`discountType` が `amount` なのに `ratePercent` に
値が入っている」といった呼び出し側の凡ミスをコンパイラは検出できない。
コンストラクタを型ごとに分けることで、そもそも「意味のない組み合わせ」を
作れないようにしている。

## なぜ now を引数で渡すのか

`IsExpired` と `Use` はどちらも「現在時刻」を必要とするが、ドメイン層の
メソッド内部で `time.Now()` を直接呼び出すことはしていない。代わりに
呼び出し側（ユースケース層）が `now` を明示的な引数として渡す設計にしている。

理由は「時刻もまたテストの入力の一つである」という考え方による。もし
`time.Now()` を内部で呼んでしまうと、期限切れの境界値（有効期限ちょうど、
1 秒前、1 秒後など）をテストする際にテスト実行時刻に依存してしまい、
再現性のあるテストが書けなくなる。`now` を注入可能にすることで、ドメイン層
は完全に決定的（deterministic）に振る舞い、任意の時刻を起点にしたテストを
容易に書けるようになる（`coupon_test.go` の `TestCoupon_Use` を参照）。

## 注文フローとの関係

本コンテキストはクーポンの発行・参照（`IssueCouponUseCase` /
`GetCouponUseCase`）のみを提供し、クーポンを実際に注文へ適用する処理は
含まない。クーポンの適用（`Use` の呼び出しと割引額の計算）は、注文確定
（`order` コンテキストの place-order ユースケース）側が `coupon.Repository`
を通じてクーポンを取得し、`DiscountFor` で割引額を求め、`Use` で消費を記録
する、という形で行われる想定である。

これは cart コンテキストが catalog の実在確認を注文確定まで遅延させている
のと同じ設計判断である。coupon コンテキストは「クーポンという概念そのもの
の整合性」だけに責任を持ち、「クーポンをいつ・どの注文に適用するか」という
決定は注文コンテキスト側に委ねることで、コンテキスト間の結合を弱く保って
いる。
