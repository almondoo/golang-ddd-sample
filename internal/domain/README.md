# domain 層

## この層の役割

`internal/domain` は DDD（ドメイン駆動設計）における「ドメイン層」であり、
このリポジトリで最も重要かつ最も安定しているべき層である。ここには
「ECサイトとは何であり、どう振る舞うべきか」というビジネスルールそのものを
表現するコードだけを置く。

各コンテキスト（catalog / cart / order）は、この `domain` パッケージの
下にサブパッケージとして追加されていく想定である
（例: `internal/domain/cart`, `internal/domain/order`）。

## 依存関係のルール（The Dependency Rule）

ドメイン層は **何にも依存しない**。より正確に言えば、標準ライブラリと
`github.com/google/uuid` のような「ドメインの語彙を表現するための最小限の
ユーティリティ」以外には依存しない。

- ドメイン層 → 何も依存しない
- アプリケーション層 → ドメイン層に依存する
- インフラストラクチャ層 → アプリケーション層・ドメイン層に依存する
- プレゼンテーション層 → 主にアプリケーション層に依存する。ただし
  `internal/presentation/controller/response.go` はエラーを HTTP ステータスへ
  分類するために `domain/shared` のエラー種別（`shared.ErrNotFound` /
  `shared.ErrConflict` / `shared.IsDomainRuleError`）を直接参照する。外側から内側への依存は
  オニオンアーキテクチャで許容される（禁止されるのは内側から外側への依存）ため、
  この参照自体は依存性のルールに反しない。

依存の矢印は常に「外側から内側へ」しか向かない。これはクリーンアーキテクチャや
ヘキサゴナルアーキテクチャで言われる「依存性のルール」であり、DDD の
戦術的パターンを実践するうえでの大前提である。この向きを守ることで、
「DB を PostgreSQL から別の何かに変えたい」「HTTP ではなく gRPC で公開したい」
といった技術的な決定を、ビジネスルールに一切手を入れずに行えるようになる。

## なぜここに GORM を置かないのか

GORM はデータベースへの永続化という「技術的関心事」を扱うライブラリである。
もしドメイン層のエンティティ（例: `Cart` 構造体）に GORM のタグ
（`gorm:"column:..."`）を直接書いてしまうと、ドメイン層が GORM という
特定の技術に縛られてしまい、
- ドメインモデルの設計が「DB テーブルに素直にマッピングできる形」に
  引きずられてしまう（例: 値オブジェクトを分けたいのに 1 テーブル 1 構造体に
  寄せてしまう）
- GORM を別の ORM に差し替えたくなったときにドメイン層まで書き換えが必要になる

という問題が起きる。そのため本サンプルでは、ドメイン層の集約・値オブジェクトと、
GORM 用の永続化モデル（`internal/infrastructure` 配下に置く）を明確に分離する
「データマッパー（Data Mapper）」パターンを採用する。両者の変換は
インフラストラクチャ層のリポジトリ実装が担う。

## この層に置くもの

- **エンティティ（Entity）**: 識別子によって同一性が決まるオブジェクト。
- **値オブジェクト（Value Object）**: 値そのもので同一性が決まる不変のオブジェクト。
  本リポジトリでは `internal/domain/shared` の `Money` がその代表例である。
- **集約（Aggregate）とその集約ルート（Aggregate Root）**: 整合性を保つ単位として
  まとめられたエンティティ・値オブジェクトの集まり。外部から集約内部の
  エンティティを直接操作させず、必ず集約ルート経由で操作させることで、
  不変条件を常に守らせる。
- **リポジトリのインターフェース**: `type CartRepository interface { ... }`
  のように、永続化の「契約」だけをドメイン層で定義する。実装は
  インフラストラクチャ層が担う（依存性逆転の原則）。
- **ドメインサービス**: 単一のエンティティ・値オブジェクトに責務を置けない
  ビジネスロジック（複数の集約をまたぐ計算等）を置く。
  ただし本サンプルには実例がない。各コンテキスト（catalog / cart / order
  など）は集約を 1 つずつしか持たず、同一コンテキスト内の複数集約を
  またぐロジックが存在しないため未使用である。コンテキストをまたぐ
  調整（`PlaceOrderUseCase` が cart・catalog・inventory・coupon を
  横断する等）はドメインサービスではなく application 層の責務であり、
  これは置き違いではなく正しい配置である。ドメインサービスがどのような
  場面で必要になるかは [`docs/ddd/domain-service.md`](../../docs/ddd/domain-service.md)
  を参照。

## internal/domain/shared について

`shared` パッケージは、特定のコンテキスト（catalog / cart / order）に
属さない、複数のコンテキストで再利用される「共有カーネル（Shared Kernel）」を
置く場所である。`Money` のような汎用的な値オブジェクトや、
`ErrNotFound` / `ErrConflict` / `DomainRuleError` といった共通エラー種別をここに置く。

共有カーネルは便利だが濫用すると各コンテキストの独立性を損なうため、
「本当にどのコンテキストでも同じ意味を持つ、安定した概念」だけを置くべきである。

`ProductID` / `CustomerID` / `OrderID` のような ID 型は共有カーネルには
置かず、各コンテキストがそれぞれ独自に重複定義している（詳細は
「catalog への ID のみの参照」等、各コンテキストの README を参照）。
この重複には、生成時の空文字チェックのようなバリデーションロジックが
11 の ID コンストラクタ（7 ファイル）にコピーされるという保守コストも
伴う。ID 型の対照表は
docs/context-map.md を参照（同一 UUID 空間を共有する型どうしの対応が
一覧できる）。

なお、生成コンストラクタ（例: `NewCart` や `shared.NewID()`）はドメイン層
の中で ID（UUID）を生成しており、これはドメイン層内の非決定性である。
`coupon.Coupon.IsExpired` が「時刻もまた入力である」として `time.Now()` を
ドメイン層で呼ばずアプリケーション層から注入させているのと同種の問題に
見えるが、本サンプルでは ID 生成は許容する判断をした。時刻と異なり、
テストの検証内容が生成された ID の値そのものに依存する場面がないため
（`ReconstructOrder` 等で既知の ID を注入すればよく、非決定性がテストの
再現性を損なわない）である。
