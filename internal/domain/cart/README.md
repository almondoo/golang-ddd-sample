# cart コンテキスト（ドメイン層）

## 集約の境界

`Cart` を集約ルートとし、`CartItem`（明細）を内部エンティティとして持つ。
集約の識別子は `CustomerID` であり、専用の `CartID` は発行しない
（「1 顧客につきカートは常に 1 つ」という業務ルールをそのまま識別子選択に
反映している）。カート集約の外から `CartItem` を単独で操作する API は
存在しない。これは、明細の追加・削除・数量変更に伴う不変条件
（数量は 1〜99、明細は最大 20 件まで）を、必ず `Cart` のメソッド経由で
守らせるためである。

## なぜカートは価格を持たないのか

カートは「何をいくつ欲しいか」という顧客の意思表示だけをモデリングし、
金額計算は一切行わない。理由は次の 2 点である。

1. カートに入れてから実際に注文するまでの間に商品価格が変動しても、
   カート側は何も追随して更新する必要がない。
2. 「カートに入れた時点の価格」と「注文時点の価格」のどちらを正とするか、
   という曖昧な業務ルールの決定をカートコンテキストが背負わずに済む。
   価格の確定は注文（order）コンテキストが catalog の最新価格を参照して
   行う責務とする。

参照画面で金額を表示したい場合は、ドメイン層を経由せず、クエリ側
（`internal/application/cart/query`、`internal/infrastructure/persistence/cart_query_service.go`）
で cart_items テーブルと products テーブルを SQL レベルで結合して求める。
これは CQRS 的な発想であり、「書き込み側（ドメインモデル）は整合性の
番人」「読み取り側は表示に必要な形へ自由に加工してよい」という
役割分担に基づく。

## catalog への ID のみの参照

カートは商品を `cart.ProductID`（このコンテキスト専用の型）で参照し、
catalog パッケージを import しない。値としては catalog 側の商品 ID と
同じ UUID 文字列を共有するが、型としては別物である。境界づけられた
コンテキスト（Bounded Context）同士が互いの内部モデルに依存し始めると、
一方の変更がもう一方に波及する強い結合が生まれてしまう。ID という
小さな型を重複させるコストは、コンテキスト間を疎結合に保つ利益に
比べれば十分に小さい。

また `AddItem` は追加時点で商品が catalog に実在するかどうかを検証
しない。存在検証は注文確定（より重い操作）のタイミングまで遅延させる
ことで、カートへの追加が catalog の可用性に左右されない軽量な操作で
あり続けられるようにしている。トレードオフとして、実在しない商品 ID が
一時的にカートに紛れ込む可能性はあるが、それは注文確定時に検出すれば
よい、という判断である。
